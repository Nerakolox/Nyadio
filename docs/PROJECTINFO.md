# 多协议音频聚合中转枢纽 · 整体方案

## 1. 目标与约束

做一个**中国大陆可访问的、多协议聚合的音频中转枢纽**:从任意来源协议(Icecast、HLS、HTTP 直推流、yt-dlp 直播、本地源……)聚合输入,内部统一规范化为一条标准音频流,再以多种输出协议(HLS、HTTP 直推流、Icecast 挂载……)同时对外提供。

Minecraft NetMusic 模组的大喇叭所需的、干净的、以 `.m3u8` 结尾的 http(s) URL,只是其中**一个输出面**;同一路流也能同时供 VLC、浏览器 `<audio>`、其他模组等任意客户端消费。**不限题材**——题材由你接入了哪些源决定,本系统是基础设施而非一个被策展的电台。

NetMusic 的硬约束依然要满足:它只认干净的 `.m3u8`,不认带鉴权参数的链接、不认 Icecast 这类非 HLS 流、不认相对路径的段。核心判断也不变:**问题是"协议适配",不是"找电台"。** 只是现在把它从"造一条干净 HLS"升级成"两端都做协议归一化"。

## 2. 技术选型

后端用 Node.js 跑一个轻量 HTTP 服务;转码与协议归一化用 ffmpeg(独立系统程序,非库,由 Node 以子进程方式调用);前端用 React(Vite 构建成纯静态 SPA,只做展示);进程管理用 PM2;最前面由 nginx 做 TLS 终止与反向代理(本方案不展开其配置);HLS 段文件放在 tmpfs 内存盘上。

这套里 **ffmpeg 实际是两端的万能适配器**:进口侧它的 `-i` 几乎能吃任何输入协议;出口侧它能复用同一份编码、复用(mux)成多种输出协议。

## 3. 整体架构

整体模型是一句话:**多协议进 → 归一化 → 多协议出。**

音频数据的流向:**任意上游协议 → ffmpeg(解码并统一编码成一条标准 AAC 流)→ tee 扇出到多个输出面 → Node 读取并对外提供 → nginx 反向代理 → 跨境 → 各类客户端(NetMusic / VLC / 浏览器 / ……)。**

关键取舍有两条。其一,**一次解码、一次编码、多协议扇出**:每条聚合频道只用一个 ffmpeg 把上游解码、统一编码一次,再 tee 给多个封装输出,而不是每种输出协议各跑一个 ffmpeg(那样 CPU 翻倍)。其二,**所有对外输出都由 Node 后端经手**,nginx 仅作透明前门(TLS + 反代),不直接吐静态。

进程控制关系不变:ffmpeg 是独立操作系统进程,由 Node 启停;Node 管它的"生死",不管它的"数据"。

### 输出面(全协议输出的现实边界)

真正值得做的输出面就那几个,但架构上每多挂一个只是 tee 多接一路,廉价。所有流路径统一在 `/stream/` 前缀下,跟前端 SPA 路由(`/`、`/channels`、`/admin/*`)和 `/api/*` 彻底隔离,避免 slug 命名空间冲突。

- **HLS 面**:写 m3u8 + 段到 tmpfs,对外路径 `/stream/:slug/index.m3u8` + `/stream/:slug/seg_*.aac`,给 NetMusic、网页 hls.js。
- **HTTP 直推流面**:输出一条连续的 AAC,由 Node 读管道后广播给任意数量的 HTTP 听众,对外路径 `/stream/:slug/audio.aac`,供 VLC、浏览器、多数播放器直接吃。
- **Icecast 挂载面(可选)**:把流推到一个 Icecast 挂载点,让 Icecast 自己扇出,把带宽压力从 Node 卸下来。

NetMusic 的 `.m3u8` 只是 HLS 面的一个 URL,不是系统的全部目的。

## 4. 组件职责

| 组件 | 角色 | 说明 |
| --- | --- | --- |
| nginx | 前门 | 终止 TLS,把全部请求反代给 Node;本方案中不直接服务静态 |
| Node (Fastify) | 唯一对外出口 + 编排者 | 服务 React 静态、`/api`、`/admin`、`/stream` 各输出面;按需启停 ffmpeg;维护频道注册表与 ConfigStore 单例 |
| PostgreSQL + Prisma | 持久化层 | 频道/源/标签/投稿/管理员/AppConfig 全局配置 |
| ffmpeg | 两端协议适配 + 转码 | 独立程序,被 Node spawn;入口吃任意协议,出口 tee 成多协议;音频数据不经过 Node 逻辑层 |
| 入口适配器 | 多协议聚合 | 每种来源协议一个分支,知道各源怪癖(HLS token、yt-dlp 管道、Icecast 连法),翻成相应的 ffmpeg 输入 |
| 出口多路复用 | 全协议输出 | 把一份归一化编码 tee 成 HLS / 直推流 / Icecast 等多个面 |
| React (Vite) | 展示层 | 拉频道目录、显示 `playState`、列出各输出面的 URL;管理面提供 7 个页面(含 `/admin/settings`);纯静态 |
| tmpfs | HLS 段缓冲 | 内存盘,扛段文件高频读写,不磨 SSD |
| PM2 | 守护进程 | 运行 Node,fork + 单实例,崩溃自启、开机自启 |

## 5. 关键设计

### 入口:源抽象(多协议聚合)

多种来源统一收敛在一个类型后面:Icecast、已经是 HLS 的第三方源、HTTP 直推流、yt-dlp 拉的直播、本地循环歌单……每种对应一个入口适配器。由于 ffmpeg 的 `-i` 本身就能识别绝大多数协议,"多协议进"本质上就是给适配器多加分支,处理各源的鉴权/管道等怪癖即可。新增一种源只动这一处。

### 出口:多路复用(全协议输出)

每条频道一次 decode、一次 encode 成标准 AAC,然后 tee 扇出到上面列的各输出面。新增一个输出协议 = 多挂一路 tee,不重复转码。各客户端按需选择自己要的那个面的 URL。

### HLS 形态

HLS 面输出标准直播 HLS:固定时长分段、滑动窗口只留最近几段(旧段删除,占用恒定)、不写结束标记(播放器据此当持续直播、周期轮询要新段)。这正好满足 NetMusic 的干净 `.m3u8` 约束;NetMusic 支持直播 HLS 已由"央广固定 m3u8 能稳定播放"间接验证。

### 按需启动 + 心跳

因为输出都过 Node,Node 直接看到每次播放列表轮询(以及直推流的连接)。于是:某频道第一次被请求时懒启动 ffmpeg;之后每次轮询/连接刷新存活心跳;空闲超时回收整条频道(连同它的所有输出面)。逻辑都在 Node 内完成,不需要额外子请求机制。直接收益:没人收听时 CPU 趋近于零。

对外 `playState` 收敛为 4 态(`live` / `preparing` / `unavailable` / `inactive`),前端按这 4 个状态画 UI,内部 `state` 实现细节不外露。频道排序按「在线优先 → 热度 → 字母」,热度采用「直推流连接累计 + 每日 ×0.9 指数衰减」(详见 spec/01-data-model.md),HLS 听众不计入热度。

(将来若让 nginx 直接静态吐 HLS,Node 看不到段请求,那时才需用 nginx 的 `auth_request` 把轮询转成心跳回调。当前结构不需要。)

### 可调参数:AppConfig 落库

频道并发上限、HLS 段时长/窗口、空闲超时、最大重试、投稿限流等运行时阈值统一进数据库 `AppConfig` 键值表,由 SUPERADMIN 在 `/admin/settings` 页面在线调整,保存时通过 `ConfigStore.refresh()` 主动推到内存与依赖模块。env 只留 `DATABASE_URL` / `JWT_SECRET` / `HLS_DIR` / `PORT` / `HOST` 等部署/秘密强相关变量。

### TLS

由 nginx 终止,Node 内部跑纯 http,客户端拿到 nginx 那侧的 https URL。

## 6. 性能评估

**CPU(ffmpeg)不随输出面增多而上涨。** 每条频道只解码、编码一次,tee 扇出几乎不耗 CPU。音频转码本就轻,单路直播只需 1 倍速,约占一个核个位数百分比;并发数被频道上限封顶,加按需启动通常只跑在听的频道。(吃 CPU 的是视频转码,音频几乎不算事。)

**带宽(Node)随听众数线性增长。** 每听众即码率,128 kbps ≈ 16 KB/s。

| 同时在线听众 | 总带宽 |
| --- | --- |
| 10 人 | ≈ 1.3 Mbps |
| 100 人 | ≈ 13 Mbps |
| 1000 人 | ≈ 128 Mbps |

HLS 面是稀疏短请求(每约 6 秒一次轮询 + 一个约 96KB 段),Node 处理轻松。**直推流面则是真·长连接**,每个听众 16KB/s 持续流过 Node——量仍小,但如果直推流听众很多,就把那一路改成推 Icecast,让 Icecast 扛扇出,带宽不再压在 Node。tmpfs 上几路段加起来不到 1MB。

**结论:** 自用或小社区规模几乎零压力,1–2 核 VPS 用不满,香港三网大宽带对音频严重过剩。压力唯一会冒头处仍是"总听众 × 16KB/s 逼近线路带宽",需几百人同时听;届时 HLS 面交还 nginx 静态、直推流面交给 Icecast 即可。

## 7. 公开暴露的安全底线

公开化是最需认真对待的部分——能按 URL 拉流转推的公开服务不设防即等于开放代理,且输出面越多、对外暴露面越大。

读操作(频道目录、各面 URL)可公开,但新增/编辑源**必须鉴权**。用户提供的 URL 必须过 SSRF 校验,拦私网段与云元数据 IP,防探内网/偷密钥;因 URL 最终传给 ffmpeg,含 shell 元字符的一律拒绝。`/api` 限流、并发频道封顶,防算力/流量被刷爆(并发上限走 AppConfig)。管理员 JWT 校验在 `onRequest` 钩子里**每次查 DB 验证 disabled**,踢人即时生效,不留 8 小时 token 漂移期。公开重推第三方电台存在版权风险,需自行评估。

## 8. 部署要点

tmpfs 挂载存 HLS 段,所有者为运行 ffmpeg 的用户,nginx/Node 可读。系统装 ffmpeg(用 yt-dlp 源则一并装 yt-dlp;用 Icecast 输出面则部署一个 Icecast 服务)。后端由 PM2 以 **fork 模式、单实例**运行——频道注册表是进程内状态,绝不能开 cluster;配置崩溃自启与开机自启。前端 Vite 构建为静态。nginx 前门只需 443 + 证书 + 反代到 Node(配置后议)。

## 9. 网络结论

128k 音频跨境带宽需求极低(16KB/s 量级);香港三网大宽带对电信/联通/移动均优化,晚高峰够用,HLS 缓冲窗口吸收抖动;大陆访问香港无需 ICP 备案。

## 10. 演进路径

直推流听众多 → 该面改推 Icecast,卸载扇出。HLS 听众多 → 该面改 nginx 静态吐 + 心跳机制,音频不再过 Node。鉴权正式化 → JWT 换 OAuth2 / 第三方登录。需要更复杂权限 → AdminUser 表扩展资源级 ACL。需要更多输出协议(DASH 等)→ 多挂一路 tee 即可。若彻底去掉 nginx → 再让 Node 自己承担 TLS。yt-dlp 源 → 入口适配器多加一个分支,处理直播链接刷新。

---

**一句话概括:** 多协议进、归一化、多协议出——ffmpeg 在两端做协议适配并"一次解码一次编码、tee 扇出多个输出面",Node 统一对外吐(React/`/api`/`/admin`/`/stream/:slug/*` 各输出面)并按需编排频道,nginx 当透明前门管 TLS 与反代,PostgreSQL + Prisma 做持久化(频道/源/标签/投稿/管理员/AppConfig),PM2 守后端。NetMusic 的 `.m3u8` 只是众多输出面之一;音频码率小到性能上几乎免费。
